# Progressive web app

The Svelte frontend at `/new` can be installed as HAWKI through the browser's install command. On iOS, use Safari's **Add to Home Screen** action. The manifest launches the app in a standalone window.

## Deployment

Serve the application over HTTPS, or localhost for development testing. Build the frontend with `bin/env npm run build`. Service worker registration runs only in production builds on pages with a manifest link. Vite development mode does not register a worker.

The worker source is `resources/js/kernel/pwa/service-worker.ts`. The build runs a strict TypeScript check with the WebWorker library, then bundles it into `public/sw.js` using esbuild. This generated file is ignored by Git and copied into the production Docker image. For worker-only changes, run `bin/env npm run build:pwa`; use `bin/env npm run check:pwa` for type checking alone.

The web server must serve these public files directly, without authentication or an SPA rewrite:

- `/manifest.json`, with a JSON content type
- `/sw.js`, with a JavaScript content type
- `/pwa/offline.html` and `/pwa/icons/`

Keep the manifest and worker on the application's origin even when other assets use a CDN. The app ID, start URL, and scope are `/new`, matching the frontend router. Deployments that change this route must update the manifest, registration scope, and worker's navigation filter together.

Icon source SVGs are in `public/pwa/icons/`. Run `bin/generate-pwa-icons` with ImageMagick installed to regenerate the PNGs after changing the artwork.

## Offline behavior and updates

The service worker caches the public offline page and downloaded frontend assets. Navigation to `/new` or its descendants uses the network and shows the offline page if the request fails. It preserves server error responses. The page offers a retry link and English and German instructions without loading the app or its translation service.

Hashed JavaScript, CSS, fonts, images, and WASM files under `/build/assets/` use cache-first delivery. After a controlled page downloads a file, later requests can use the local copy, including offline. A changed Vite hash creates a new URL, so new builds fetch new files. The four PWA PNG icons use network-first delivery with a cached fallback to keep their stable URLs fresh. The runtime cache holds at most 256 files and evicts the oldest entries.

Only files on the application's origin are eligible. Assets served from a separate CDN origin retain their normal browser caching. Requests with query strings, authorization or range headers, or `cache: 'no-store'` bypass the worker cache. Responses must have the expected content type and status 200 without a redirect. Responses marked `private`, `no-store`, or `no-cache` are not stored. Cache storage failures leave online loading working.

Chat, sign-in, and files need a network connection. The worker does not cache authenticated HTML, API responses, chat messages, or attachments. Existing frontend storage behavior is unchanged. Asset caching starts after the worker controls the page; it does not download the entire build in advance or make authenticated navigation available offline.

Worker updates wait for open app windows to close before activating. They do not force a reload during a chat. When changing the offline page, bump its cache version in `resources/js/kernel/pwa/service-worker.ts` so the changed worker installs the new page. Bump the asset cache version when changing caching rules. Activation removes only older caches belonging to this worker.

## Verification

Run `bin/env npm run test:pwa` for the worker and registration tests, then `bin/env npm run build`. The PWA tests first type-check and build the TypeScript worker, then exercise the generated JavaScript used by browsers.

For browser verification, serve the production build and open `/new`:

1. In developer tools, inspect the manifest, icons, and active service worker. Install the app and confirm that it opens `/new` in a standalone window.
2. Switch the browser offline and reload `/new` and a nested frontend URL. Confirm that the offline page appears and its retry link is keyboard accessible. Reconnect and retry.
3. Inspect Cache Storage. The offline cache should contain only the offline page. The asset cache should contain only eligible build files and PWA icons, including after sign-in and chat use. Load a cached asset offline and confirm it remains available.
4. Confirm that API requests, attachments, and legacy routes retain their normal network behavior.
5. Change the cache version and reload online. The new worker should wait until all controlled windows close, then activate when the app is reopened.

An already installed worker remains installed if you switch the same origin back to Vite development mode. Unregister it in developer tools when testing development behavior.

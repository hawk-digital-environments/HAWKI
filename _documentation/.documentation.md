# HAWKI Documentation Principles

How HAWKI documentation is structured and written. Apply this to every doc change.

## Source of truth

The `documentator` skill (`~/.claude/skills/documentator/SKILL.md`) is the canonical style guide. This file captures the project-specific decisions layered on top of it. When the skill and this file agree, this file wins on HAWKI specifics; when they differ on style, the skill wins.

## What docs are for

Every page answers three questions, in this order:

1. Which concepts are there?
2. How do I work with them?
3. What is good to know / where are the dragons?

Not: "what fields does this model have." The reader opens the class for that. Tables of model properties, method signatures, or enum cases do not belong in prose — they rot the moment code changes and teach the wrong level of abstraction.

## Kind-first, then domain

Backend docs (`500-Backend/`) route the reader by *kind of page* first, domain second:

- **Tutorials** — one concrete scenario, walked end-to-end. The cleanest path in the codebase, not the most interesting one.
- **Concepts** — "how do I use pattern X." One page per pattern. This is the hub everything else links to.
- **HTTP API** — request/response contracts and conventions.
- **Domains** — what each domain *does*, not how patterns work. Domain pages link to Concepts; they do not redefine them.
- **Reference** — lookup catalogues (artisan commands, shared utilities, infrastructure macros). Honestly framed as "code is truth."

A concept page lives exactly once. Repositories, ServiceLocator, contextual scopes, casts, events, value objects — each has one home. Every domain that uses the pattern links; none redefines.

## Audience

One page, one audience. When a page must serve two, default to **contributor** primary, plugin-author secondary (links out).

Plugin-author content belongs in `_documentation/700-Authoring-Plugins/` once the plugin code is implemented. Until then:

- Live, usable-today extension points are covered in `500-Backend/200-Concepts/220-Extending-HAWKI.md`.
- The v3 plugin system design (clearly marked as not-yet-implemented).

## Anti-patterns to avoid

- **Apology framing.** "Why this exists / not over-engineering" as the lead. Lead with how-to. Rationale is one short paragraph, not a section.
- **Method / field / property enumeration tables.** Link to the class instead. The constants in `WellKnownCapabilities`, the columns of `Message`, the methods of `LocaleService` — all live in code.
- **Scattered concepts redefined in multiple pages.** One home, link everywhere. If `LocaleService` is documented in two places, one of them is wrong.
- **Tech-debt warnings at the top of a domain page.** Link to `500-Backend/900-Technical-Debt.md`. Do not restate the debt in every domain that touches a flagged class.
- **Duplicating artisan commands or extension points in domain pages.** Reference pages own the catalogues; domains link.
- **Doc-fighting.** Notes that correct older docs ("older documentation may incorrectly state…"). Fix the old doc or delete it; do not carry the feud forward.

## Code in docs

- **Real, copyable code** where the reader reproduces the shape. Keep every line that carries a convention: `#[Singleton]`, `readonly`, `#[Config('...')]`, `#[CurrentUser]`, return types, `@api` markers. Trim unrelated lines; never simplify a copyable example.
- **Simplified, labelled code** where the reader needs the idea, not the implementation. Say "simplified view from `src/...`" and link to the real file. Keep the shape honest.
- **Never paste a full class body** as a "reference implementation." Name the class, link it, extract the load-bearing lines for each concern with their own prose context.

## Architecture over enumeration

Use mermaid for anything with flow or ordering. Use prose for rationale. Use tables for layer responsibilities, navigation ("I want to → read"), and directory anatomy — not for listing methods or fields.

## Temporary constructs

Deprecated transition scaffolding (`OldUiBridge`, the Svelte snippet bridge, `AssetCacheBusting`) is documented where it lives in the codebase, not in domain pages.

## Migration discipline

When restructuring, move the original content out of the way first (`500-Backend-old/`) and preserve git history. Write the new tree folder by folder, starting with the Concepts hub since everything links to it. The archived directory stays reachable until the new tree is complete; then it is deleted in one commit.

## Accuracy — verify before writing

Docs that describe the wrong thing are worse than no docs. Before writing about a class, a flow, or a frontend consumer:

- **Read the actual source.** Do not infer behaviour from the class name, from older docs, or from how a similar system works elsewhere. If the file path is known, open it. If the frontend path changed (e.g. `resources/js/data/keychain/` → `resources/js/kernel/keychain/`), check the real path before writing it.
- **Do not fabricate cross-domain connections.** If you are not sure whether passkeys are part of the auth domain or the encryption domain, do not write a "Passkey integration" section in the auth page. Ask or check the code; if it turns out to be wrong, remove it.
- **Distinguish server-side from browser-side.** HAWKI has a standalone server-side crypto library (`hawk-hhg/hawki-crypto`) and separate browser-side crypto helpers. Do not conflate them.
- **Distinguish framework internals from custom code.** Laravel Sanctum handles session/token transport; HAWKI's auth domain is the login procedure (LDAP, OIDC, Shibboleth). Do not document Laravel's built-in behaviour as if it were a HAWKI feature, and do not put framework internals in the Domains section — they belong in HTTP API or a cross-reference to Laravel's docs.

## Sidebar structure

Docusaurus auto-generates the sidebar from the filesystem. Directories with numeric prefixes become collapsible groups; `index.md` is the landing page; `_category_.json` sets the label. Files with numeric prefixes inside a directory are ordered children. To create a sub-section (e.g. ServiceLocator under Dependency Injection), convert the flat `.md` file into a directory with `index.md` + child files — do not leave sub-pages as flat siblings with a letter suffix (`160a-`, `160b-`).

Do not use `sidebar_position` frontmatter. The numeric file/folder prefix is the sole ordering mechanism.

## Deprecation and "subject to change"

Mark things honestly:

- **DEPRECATED / LEGACY** (`:::danger`) — the code exists but is scheduled for removal. Always state what replaces it and link to the [Technical Debt Register](500-Backend/900-Technical-Debt.md).
- **Subject to change** (`:::warning`) — the API exists and works but will change shape (e.g. a container-tag pattern that will become a registry).
- **Not yet implemented** (`:::warning` or `:::note`) — the design exists but no code ships yet.

Do not document deprecated behaviour as if it were the recommended pattern. A reader who copies a deprecated example has been misled.

## Security advisories

When documenting a security mitigation (e.g. the SSRF macro), explain what vulnerability it fixes and why the mitigation is necessary — but do not overstate the scope. If the mitigation is manual (the developer must call `Http::getSsrfSafe()`; there is no global override), say so. "Every HTTP call goes through this macro" is wrong when the developer has to opt in per call.
